# tudu 크레딧 및 토큰 시스템 계획

## 목적

AI 분석 비용과 학습 보상을 서로 다른 잔액으로 운영한다. 크레딧은 AI 문제 분석에 사용하고, 토큰은 문제 풀이와 오답 복습을 통해 얻는 게임 보상으로 사용한다. 두 잔액을 분리해 학습 보상 때문에 AI 사용량이 무제한 늘어나거나, 분석 크레딧이 게임 재화처럼 혼동되는 일을 막는다.

## 제품 원칙

- **크레딧은 AI 사용 한도다.** 분석 요청이 성공적으로 결과를 반환할 때 설정된 크레딧을 차감한다. 분석 실패나 서버 오류에는 차감하지 않는다.
- **토큰은 학습 보상이다.** 정답 제출, 풀이 완료, 오답노트 복습에 대해 정해진 규칙으로 지급한다.
- **크레딧과 토큰은 분리하되 제한된 환전 경로를 둔다.** 현재 제안 환율은 1크레딧 = 20토큰이며, 환전은 서버 원장에서 원자적으로 처리한다.
- **보상은 학습 이벤트당 한 번만 지급한다.** 재전송, 새로고침, 같은 답 반복 제출로 중복 획득할 수 없어야 한다.
- **보상은 결과와 이유를 사용자에게 보여준다.** 잔액 변화와 함께 `문제 첫 시도 정답 +10 토큰`처럼 구체적인 내역을 표시한다.

## 제안 잔액 규칙

아래 수치는 초기 가설이다. 비용과 학습 데이터를 확인할 수 있도록 서버 설정값으로 관리하고, 상수로 UI에 박아두지 않는다.

| 이벤트 | 크레딧 변화 | 토큰 변화 | 지급 조건 |
|---|---:|---:|---|
| Flash 분석 성공 | -2 | 0 | 분석 결과가 정상적으로 생성된 뒤 차감 |
| 통화 학습 분석 성공 | 가격 확정 전 | 0 | 분석 결과가 정상적으로 생성된 뒤 차감; 음성 사용량 과금은 별도 정책 |
| AI 문제 분석 실패 | 0 | 0 | 예약 차감이 있었다면 전액 환불 |
| 새 문제 첫 시도 정답 | 0 | +10 | 문제 세션당 1회 |
| 새 문제 두 번째 시도 정답 | 0 | +6 | 첫 시도에 오답 후 두 번째에 정답 |
| 두 번 오답 후 풀이 확인 완료 | 0 | +2 | 풀이를 열고 완료 동작을 선택했을 때, 세션당 1회 |
| 오답노트 복습 첫 시도 정답 | 0 | +12 | 해당 오답노트의 복습 보상 최초 1회 |
| 오답노트 복습 두 번째 시도 정답 | 0 | +8 | 해당 오답노트의 복습 보상 최초 1회 |

크레딧 지급 방식은 아직 정하지 않았다. 일일 무료 지급, 가입 보너스, 구독 또는 유료 충전 가운데 어떤 방식을 쓸지 결정하기 전까지 분석 비용과 초기 크레딧 수량은 조정 가능한 정책값으로 둔다. BYOK 사용자의 크레딧 차감 여부도 출시 전 확정한다. 권장안은 서버 Gemini 키 사용 시 크레딧을 차감하고, 사용자 본인 키 사용 시 앱 크레딧은 차감하지 않는 방식이다.

토큰은 학습 활동 보상과 테마 상점 결제에 사용한다. 크레딧 환전 외에 현금 가치가 있는 재화처럼 안내하지 않으며, 환율과 공급 한도를 명확히 보여준다.

## 학습 모드별 크레딧 가격과 환전

| 학습 모드 | 사용자 표시 | 제안 비용 | 경험 |
|---|---|---:|---|
| `speed` | 기본 | 2크레딧 | 문제 분석 및 단계별 풀이 |
| `deep` | 통화 | 미정 | 문제 촬영과 실시간 음성 학습 |

사용자에게 보이는 모드 이름은 **기본**과 **통화**로 한다. 기본은 현재처럼 촬영 화면에서 문제를 분석하고 단계별 풀이로 진행한다. 통화는 음성으로 AI와 대화하며 문제를 단계별로 풀어가는 학습 경험이다. Pro, Flash 같은 모델명은 사용자 모드 이름으로 노출하지 않는다. 내부 `speed`·`deep` 식별자는 기존 호출부 호환을 위해 구현 시점까지 유지할 수 있다.

현재 화면은 Flash/Pro 선택을 제공하지만 Gemini 호출부에서는 두 모드 모두 `gemini-flash-lite-latest`를 사용한다. 가격을 적용하기 전에 Flash 분석 경로와 통화 학습 경로를 실제 서비스에 연결해야 한다. 요청 본문에 담긴 비용을 신뢰하지 않고, 서버가 검증한 모드로 비용과 기능 접근을 결정한다. BYOK는 사용자의 API 키로 호출하므로 앱 크레딧 차감 여부를 별도 정책으로 확정한다.

통화 모드는 분석 1회 비용만으로 음성 사용 원가를 대표하기 어려우므로 크레딧 가격을 아직 확정하지 않는다. 비용 모델은 분석 시작 비용과 세션 시간·발화량 등 음성 사용 한도를 함께 고려한다. 토큰은 의미 있는 학습 단계 완료나 풀이 개선에 지급하고, 단순 발화 횟수에는 지급하지 않으며 일일 상한과 세션별 중복 방지를 둔다.

### 통화 모드 진입 및 문제 촬영 흐름

1. 사용자가 모드 설정에서 `통화`를 선택하면 일반 카메라 촬영 화면을 통화 시작 화면으로 바꾼다. 기존 분석 화면과 섞지 않고 통화 진입 의도를 분명히 보여준다.
2. 통화 시작 화면에는 캐릭터 영역(캐릭터는 추후 결정)과 **“[캐릭터]와 통화를 시작하시겠어요?”** 안내, 시작 버튼을 표시한다. 촬영 화면의 주요 버튼도 `통화 시작`으로 바꾼다.
3. 사용자가 시작을 누르면 통화 세션을 열고 캐릭터가 영상통화 화면으로 전환된다. 캐릭터는 사용자에게 문제를 카메라에 비춰 촬영해 달라고 안내한다.
4. 문제 촬영 후 이미지 분석을 진행하고, 인식 결과를 확인한 다음 음성으로 한 단계씩 문제를 풀도록 대화를 시작한다.
5. 카메라·마이크 권한을 각각 필요한 시점에 요청하고, 거부된 경우 텍스트 입력 또는 권한 설정 안내와 종료 동작을 제공한다. 통화 종료 시 세션 상태와 사용량을 정리한다.
6. 통화 중에는 현재 풀이 단계, 듣기/말하기 상태, 다시 촬영, 음소거, 통화 종료 같은 핵심 조작을 큰 터치 영역으로 제공한다.

통화 모드는 음성 세션을 포함하므로, 분석 크레딧 차감 시점(세션 시작 또는 분석 성공), 음성 사용 한도, 중단·재연결 처리, 실제 원가를 기준으로 별도 가격 정책을 확정한다.

제안 환율은 **20토큰을 차감해 1크레딧을 지급**하는 방식이다. 토큰으로 AI 분석을 충당할 수 있어 크레딧 공급량을 함께 관리해야 한다.

- 환전은 서버 원장에서만 처리하고, 토큰 차감과 크레딧 지급을 하나의 트랜잭션으로 묶는다.
- 환전 단위는 20토큰으로 고정한다. 한 번에 환전 가능한 최대량과 계정별 일일 한도는 출시 전에 확정한다.
- 크레딧을 토큰으로 되돌리거나 현금으로 환급하지 않는다.
- 환율, 분석 비용, 무료 크레딧 지급은 서버 설정값으로 관리한다.
- Flash 2크레딧은 제품 가격 제안이다. 통화 학습의 가격은 음성 세션 원가와 사용 한도를 정한 뒤 확정한다.

## 확정된 제품 방향

- 토큰의 첫 사용처는 **꾸미기와 테마 해금**이다. 학습 테마, 풀이 화면의 장식 요소 등 학습 기능이나 정답 판정에 영향을 주지 않는 항목부터 제공한다.
- 크레딧과 토큰 잔액은 **사용자 계정에 연결된 서버 지갑**으로 관리한다. 브라우저 저장값은 화면 표시용 캐시로만 쓰며, 잔액의 기준으로 삼지 않는다.
- 크레딧을 토큰으로 되돌리거나 현금으로 환급하지 않는다. 꾸미기 항목은 한 번 해금하면 계정에 영구 귀속하고, 같은 아이템을 중복 구매할 수 없게 한다.
- 로그인과 데이터 저장소는 현재 프로젝트에 없으므로, 지갑 UI 구현 전에 인증 제공자와 영속 데이터베이스를 선택하고 구성해야 한다.

## 토큰 사용처: 테마 상점

첫 상점은 작은 테마 카탈로그로 시작한다. 기본 테마는 무료로 유지하고, 해금 가능한 테마는 이름·미리보기·가격·해금 여부를 보여준다. 구매 전에는 가격과 구매 후 잔액을 확인할 수 있게 하고, 잔액 부족과 이미 소유한 항목도 명확히 구분한다.

- 테마 카탈로그는 서버가 제공하는 상품 ID와 가격을 기준으로 한다. 클라이언트가 제출한 가격은 신뢰하지 않는다.
- 구매는 상품 소유권 확인, 토큰 차감, 구매 원장 기록을 하나의 DB 트랜잭션으로 처리한다.
- 구매 요청에는 멱등성 키를 사용해 재시도나 더블 탭에도 한 번만 결제한다.
- 토큰 → 크레딧 환전 요청도 멱등성 키와 원자적 거래 처리를 적용한다.
- 해금된 테마는 사용자 계정에 영구 연결하고 여러 기기에서 복원한다.
- 가격은 출시 전에 정할 운영 설정값으로 두고, 경제 테스트 뒤 조정한다. 초기 상품 수와 가격은 학습 보상 누적 속도와 함께 검토한다.
- 화폐는 장식 선택에만 영향을 준다. 학습 단계, 힌트, 정답 기회, 문제 난이도를 토큰으로 판매하지 않는다.

### 대표 사용자 흐름

1. 사용자가 계정으로 로그인하면 서버 지갑과 소유 테마를 불러온다.
2. 상점에서 잠긴 테마와 토큰 가격을 확인하고 미리보기를 연다.
3. 구매를 누르면 서버가 로그인 사용자, 잔액, 중복 소유 여부를 다시 확인한다.
4. 조건이 맞으면 토큰 차감, 거래 기록, 테마 소유권 부여를 함께 확정한다.
5. 앱은 갱신된 토큰 잔액과 해금 완료 상태를 받아 화면에 반영한다.

## 계정과 저장소 도입 결정

계정 지갑을 위해 다음 기반이 먼저 필요하다.

- 인증 제공자: 계정 생성·로그인·세션 검증을 담당한다. 계정 ID를 지갑, 거래, 보상, 구매 내역의 소유자 키로 사용한다.
- 영속 데이터베이스: 지갑 잔액, 거래 원장, 보상 수령, 테마 소유권을 저장하고 원자적 트랜잭션을 지원해야 한다.
- 사용자가 지정한 Firebase를 기준으로 Firebase Authentication과 Cloud Firestore를 우선 구성안으로 삼는다. Next.js 서버는 Firebase Admin SDK로 ID 토큰을 검증하고 Firestore 트랜잭션에서 지갑·거래·보상·구매를 갱신한다.
- 브라우저는 Firebase Authentication으로 로그인하고 ID 토큰을 서버 API에 전달한다. Admin SDK 자격 증명은 서버 환경에만 둔다.
- Firestore 문서 경로 예시: `users/{uid}/wallet/main`, `users/{uid}/walletTransactions/{transactionId}`, `users/{uid}/ownedThemes/{themeId}`. 거래 문서에는 통화, 증감, 사유, 참조 ID, 멱등성 키, 서버 시각을 기록한다.
- Firestore 보안 규칙은 지갑, 원장, 소유권 컬렉션의 클라이언트 직접 쓰기를 차단한다. 서버 API만 인증된 UID의 거래를 수행한다.
- 서버 권한 경계: 클라이언트가 잔액·보상량·가격을 정할 수 없고, 서버가 인증된 세션을 바탕으로만 변경하도록 한다.
- 계정 이관: 기존 `localStorage` 오답노트와 사용자 Gemini 키를 계정 데이터로 옮길지 별도로 결정한다. 잔액 시스템 구현을 위해 기존 데이터를 자동 업로드하지 않는다.

인증과 DB 조합이 정해지면 지갑 API, 마이그레이션, 보상 발급, 상점 구매 순으로 구현한다. 선택 전에는 실제 사용자 잔액을 생성하거나 브라우저 값으로 흉내 내지 않는다.

## 지갑 화면과 내역

- 지갑 요약은 크레딧과 토큰을 서로 구분해 표시하고, 각 통화의 사용 목적을 짧게 설명한다.
- 거래 내역에는 날짜, 변화량, 잔액 변화 사유를 표시한다. 예: `문제 첫 시도 정답 +10 토큰`, `테마 해금 −80 토큰`, `AI 문제 분석 −1 크레딧`.
- 토큰 획득 내역과 사용 내역을 필터링할 수 있게 한다. 크레딧과 토큰을 하나의 숫자로 합산하지 않는다.
- 구매가 실패하면 토큰과 소유권 모두 변경되지 않으며, 재시도해도 중복 결제되지 않아야 한다.

## 학습 흐름

1. 홈과 분석 화면에 크레딧·토큰 잔액을 각각 표시한다.
2. 분석 전에 선택한 모드의 비용(기본 2크레딧 / 통화 가격 미정)과 현재 잔액을 보여준다. 잔액이 부족하면 분석 요청을 보내지 않고 환전 또는 무료 지급 정책을 안내한다.
3. 서버가 분석 요청을 처리한다. 결과가 성공했을 때만 크레딧 거래를 확정하고, 실패하면 예약분을 되돌린다.
4. 풀이 화면은 첫 시도 정답, 두 번째 시도 정답, 풀이 확인 완료 이벤트를 구분해 보상을 표시한다.
5. 오답노트 복습은 새 문제와 같은 단계형 풀이를 사용한다. 정답 보상은 노트별 최초 복습 완료에 한해 지급한다.
6. 지갑 내역 화면에서 크레딧 차감·환불과 토큰 획득 사유를 날짜순으로 확인할 수 있게 한다.

## 기술 설계

### 현재 구조와 제약

현재 오답노트와 Gemini API 키는 브라우저 `localStorage`에 저장된다. 분석 API의 요청 제한은 서버 메모리 `Map`에 있어 프로세스 재시작 시 초기화된다. 저장소에는 사용자 인증이나 영속 데이터베이스가 확인되지 않았다. 따라서 실제 크레딧 경제를 출시하기 전에 사용자 식별과 영속 저장소를 먼저 정해야 한다. 브라우저 잔액만으로는 조작과 중복 보상을 막을 수 없다.

### 서버 원장

서버에서 잔액을 계산하고 모든 변화를 거래 내역으로 기록한다.

- `wallets`: 사용자 ID, 크레딧 잔액, 토큰 잔액, 수정 시각
- `wallet_transactions`: 사용자 ID, 통화 종류, 증감량, 사유 코드, 참조 대상 ID, 멱등성 키, 생성 시각
- 크레딧 환전의 토큰 차감과 크레딧 증가는 같은 거래 그룹 ID로 연결한다.
- 분석 거래는 요청 ID를 멱등성 키로 사용해 재시도에도 한 번만 차감한다.
- 답안 보상은 사용자 ID와 문제 세션 또는 오답노트 ID를 묶어 중복 지급을 막는다.
- 잔액 갱신과 거래 기록은 하나의 데이터베이스 트랜잭션으로 처리한다.

### 분석 요청 처리

1. 사용자와 잔액을 확인한다.
2. 요청 ID로 중복 요청인지 확인한다.
3. 충분한 크레딧이 있으면 1크레딧을 예약한다.
4. Gemini 분석을 실행한다.
5. 성공하면 예약을 차감으로 확정하고, 실패하면 예약을 취소한다.
6. 클라이언트에는 결과와 남은 잔액을 반환한다.

API 키 자체는 원장과 분리해 보관한다. 사용자별 키 전송과 로깅에서 키가 노출되지 않도록 하고, 키 문자열을 거래 사유나 이벤트 로그에 포함하지 않는다.

## 단계별 출시 계획

### 1단계: 정책과 설계

- 크레딧 지급 방식과 BYOK 차감 정책을 확정한다.
- 분석 1회 비용과 보상 수치를 설정값으로 정한다.
- 분석 실패, 취소, 시간 초과, 재시도 처리 규칙을 확정한다.
- 사용자 계정과 데이터베이스 선택을 결정한다.

**완료 기준:** 잔액이 바뀌는 모든 이벤트에 차감·지급·중복 방지 기준이 정의되어 있다.

### 2단계: 서버 잔액과 거래 원장

- 인증 제공자와 트랜잭션을 지원하는 데이터베이스를 선택·구성하고, 사용자 지갑과 거래 내역 스키마를 만든다.
- 잔액 조회, 거래 기록, 멱등성 검사를 서버에 구현한다.
- 계정 생성 시 초기 크레딧 정책을 적용한다. 초기 지급량과 지급 조건은 별도 정책값으로 확정한다.
- 사용자별 영속 요청 제한으로 현재 메모리 `Map` 기반 제한을 대체한다.

**완료 기준:** 브라우저 저장값을 바꿔도 서버 잔액과 거래 기록은 바뀌지 않는다.

### 3단계: AI 분석 크레딧

- 분석 API에 잔액 확인, 예약, 성공 확정, 실패 환불을 연결한다.
- 크레딧 부족 응답과 재시도 동작을 정리한다.
- 분석 성공·실패·중복 요청·동시 요청을 검증한다.

**완료 기준:** 성공한 분석만 한 번 차감되고 실패 분석은 비용이 남지 않는다.

### 4단계: 풀이와 오답노트 토큰 보상

- 클라이언트가 보상량을 지정하지 않고 서버가 정답 시도 횟수와 문제 세션을 확인한다.
- 첫 시도 정답, 두 번째 시도 정답, 풀이 확인 완료를 서로 다른 이벤트로 기록한다.
- 오답노트별 복습 완료 보상은 최초 1회만 지급한다.
- 반복 제출, 브라우저 새로고침, 네트워크 재시도에서 중복 지급이 되지 않도록 한다.

**완료 기준:** 정답이나 복습 조건을 충족한 세션은 정해진 보상을 한 번 받고, 같은 세션으로 다시 요청해도 잔액이 증가하지 않는다.

### 5단계: 모바일 UI와 운영 지표

- 크레딧·토큰 잔액, 분석 비용, 보상 안내, 거래 내역을 모바일 화면에 추가한다.
- 테마 상점, 아이템 미리보기, 구매 확인, 구매 완료, 잔액 부족 상태와 소유 테마 선택을 구현한다.
- 기기 변경 후 로그인해도 지갑과 구매한 테마가 복원되는지 확인한다.
- 잔액 부족·분석 실패·보상 지급 결과를 풀이 흐름을 막지 않는 문구로 안내한다.
- 분석 완료율, 크레딧 부족으로 중단된 비율, 첫·두 번째 시도 정답률, 오답노트 재방문율, 세션당 보상량을 측정한다.
- 보상 악용, 비정상 요청량, 중복 거래를 감시할 운영 화면 또는 경보를 추가한다.

**완료 기준:** 사용자가 잔액의 용도와 변동 이유를 이해하고, 핵심 학습 흐름을 모바일에서 끝까지 완료할 수 있다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 브라우저 잔액 조작 | 서버 원장을 단일 진실 원천으로 사용 |
| 분석 재시도에 따른 중복 차감 | 요청 ID 멱등성 처리와 예약·확정·환불 방식 |
| 답안 반복 제출로 토큰 무한 획득 | 서버에서 세션별 보상 횟수 제한 |
| 오답노트 반복 복습으로 보상 농사 | 노트별 최초 복습 보상, 이후 보상 없음 또는 낮은 일일 한도 |
| 크레딧 부족으로 학습 중단 | 분석 전 비용 표시, 크레딧 지급 정책과 오류 안내 제공 |
| 토큰의 쓸모가 불분명함 | 초기 토큰 보상은 가볍게 시작하고, 앱 내 사용처를 준비한 뒤 노출 확대 |
| 토큰 상점이 학습 공정성에 영향 | 첫 상품은 테마·꾸미기 전용으로 제한하고 기능상 이점을 판매하지 않음 |
| 상점 더블 탭·재시도로 중복 결제 | DB 트랜잭션, 멱등성 키, 상품 소유권 고유 제약으로 방지 |
| 개인정보·API 키 노출 | 인증·서버 로그에서 키와 답안 원문을 최소 수집하고 민감 값 제거 |

## 출시 전 결정할 항목

1. 신규 사용자와 기존 사용자에게 지급할 초기 크레딧 수량
2. 일일 무료 크레딧, 구독, 유료 충전 중 적용할 공급 방식
3. BYOK 분석에도 앱 크레딧을 차감할지 여부
4. 추천 보상 수치와 오답노트 반복 보상 한도
5. 토큰의 첫 사용처와 유료 가치 여부
6. 계정 인증 제공자와 트랜잭션 지원 데이터베이스 제공자
7. 초기 테마 상품 목록과 토큰 가격, 무료 테마 제공 범위
8. 신규 계정 초기 크레딧, 일일 무료 지급·구독·유료 충전 공급 정책
9. 기존 로컬 오답노트와 BYOK 키를 계정으로 이전할지 여부

초기 권장안은 Firebase Authentication + Cloud Firestore를 사용하고, 기본 모드는 2크레딧, 통화 모드는 문제 촬영·음성 원가와 세션 한도를 산정한 뒤 가격을 정하며, 환전은 20토큰당 1크레딧으로 운영하는 것이다. 보상량과 환전 한도는 서버 설정으로 관리하고 실제 지급·충전 정책은 분석 원가와 사용 지표를 확인한 뒤 확정한다.
